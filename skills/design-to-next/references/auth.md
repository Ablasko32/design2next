# Auth (Better Auth)

Read when sign-in is needed: accounts, dashboard, admin, webshop customer accounts. Never by default.

Auth needs a DB → Drizzle (SKILL.md) on too. SKILL.md rules still apply.

## 1. Before starting

Ask (skip what's clear):

1. **Sign-in methods:** email + password, magic link, social (which).
2. **Email verification / password reset:** needed? Both need the email service (SKILL.md section 8).
3. **Roles:** just "signed in", or roles (admin, customer...).
4. **Which routes are private.**

Check Better Auth docs (https://www.better-auth.com/docs) for current Next.js + Drizzle setup before coding. API changes; docs beat examples below.

## 2. Files

```
lib/
  auth.ts               server: betterAuth(...) config (no "server-only", see below)
  auth-client.ts        client: createAuthClient() for sign-in / sign-out forms
  db/
    schema.ts           includes auth tables (generated by Better Auth CLI)
app/
  api/auth/[...all]/route.ts   Better Auth handler (allowed: auth callback endpoint)
  (auth)/               sign-in, sign-up, reset pages
  (app)/                private routes, layout checks session
proxy.ts                optimistic redirect for private routes (or middleware.ts, check docs)
```

- Auth tables: generate with Better Auth CLI into Drizzle schema, then run Drizzle migration. Never by hand.
- Env: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, provider keys. All server only, via `lib/env.ts`.
- **`server-only` and the CLI:** CLI loads `lib/auth.ts` in plain Node, where `import "server-only"` throws. So `lib/auth.ts` doesn't import it. It still imports `lib/db` and `lib/env.ts`, which do → run CLI with `react-server` condition (there `server-only` is an empty module):

  ```bash
  NODE_OPTIONS="--conditions=react-server" <pm> dlx @better-auth/cli generate
  ```

  Check docs for current CLI name / flags. `lib/auth.ts` stays safe: its secrets come from server-only modules, and `check.sh` errors if a client component imports it.

## 3. Rules

- **Session checked on server**, in private group `layout.tsx` or page, via `auth.api.getSession({ headers: await headers() })`. No session → `redirect` to sign-in.
- `proxy.ts` check = **optimistic redirect** only (cookie present or not). Never real protection. Every Server Action / query on private data checks session again.
- Session read uses `headers()` = runtime data: **outside** `"use cache"`, inside `<Suspense>` (SKILL.md section 5). Cached queries take user id as argument, never read session.
- Server Actions: session first; none → `{ ok: false, error: "unauthorized" }`; then role check if needed.
- Sign-in / sign-up forms: react-hook-form + Zod, calling auth client. Errors never reveal whether an email exists.
- Private groups: `noindex`, blocked in `robots.ts` (SKILL.md section 9).
- Sign-in / sign-up pages: own title, `noindex`.

## 4. Checklist

- [ ] Sign-in methods, verification, roles, private routes agreed with user
- [ ] Auth tables generated by CLI, migration run
- [ ] Secrets only in `lib/env.ts`; `lib/auth.ts` without `server-only`; CLI run with `react-server` condition
- [ ] Session checked on server in every private layout, action, query (proxy only optimistic)
- [ ] No session read inside `"use cache"`; session-dependent parts in `<Suspense>`
- [ ] Private and auth pages `noindex`, blocked in `robots.ts`
- [ ] Sign-in, sign-out, sign-up (+ reset if on) tested by hand in browser
